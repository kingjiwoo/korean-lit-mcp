# 한국문학 MCP 작업 계획

작성일: 2026-10-26. 기준 문서: 「국어 수업용 한국문학 MCP 설계」(2026-10-26, 김지우).

진행 갱신: 2026-11-01. PR 00~09의 구현·교차 리뷰·CI를 마치고 GitHub PR #1~#10을 `develop`에 통합했다. 호스팅은 Vercel로 확정했고 최종 `main` 릴리스와 production 검증을 진행한다. 실제 PR과 남은 항목은 [현재 진행 상태](STATUS.md)에 기록한다.

진행 갱신: 2026-11-01. 사용자의 범위 확대 결정에 따라 고전문학·고전시가의 가능한 작품을 소규모로 제한하지 않고 제공 범위를 조사한다. 국립중앙도서관 API 키는 이미 신청 중이며, 발급 후 공식 API의 응답·원문 범위·이용 조건을 실증한다. 현대 편집·교감 텍스트, 번역·주석은 옛 작품의 저작권 만료만으로 재사용 가능하다고 간주하지 않는다. 후속 작업 계획은 13절에 둔다.

설계의 핵심인 원문 공급과 인용 검증을 먼저 구현한다. 사용자 의견을 반영해 SQLite 도입을 제외하고, API 응답은 메모리 캐시로 처리한다. 아래 범위·완료 기준은 구현을 위한 제안이며, 인터뷰와 API 실증 결과로 확정한다.

이 문서는 구현을 지시할 수 있는 작업 목록이다. 체크박스는 실제 작업과 검증이 끝났을 때만 완료로 바꾼다. 공통 작업 규칙은 [AGENTS.md](../AGENTS.md), 스킬 운영은 [SKILLS.md](SKILLS.md), 브랜치 운영은 [BRANCHING-AND-DEPLOYMENT.md](BRANCHING-AND-DEPLOYMENT.md)를 따른다.

## 1. 현재 상태와 기본 결정

- 작업 시작 시 저장소는 초기 문서만 있었다. 현재 Python 서버, 원문 파일, 테스트, 검사 설정과 컨테이너를 구현했다.
- 초기 스택 PR #1~#10을 `develop`에 통합했다. `main`은 릴리스 PR의 필수 검사를 통과한 뒤 merge commit으로 승격한다.
- Python 3.13 + FastMCP 4.1.4 + Streamable HTTP를 사용한다. 의존성은 잠금 파일로 고정했다.
- Python 환경과 의존성은 uv, lint·format은 Ruff, 타입 검사는 mypy, 테스트는 pytest로 통일한다. Markdown은 markdownlint-cli2로 검사한다.
- MVP에는 SQL DB, ORM, DB 마이그레이션, 별도 캐시 서버를 추가하지 않는다.
- 한 사람이 배포하면 누구나 MCP URL만 등록해 사용한다. 로그인·사용자 토큰·발급 페이지 없이 공개하며 기관 API 키는 운영 서버에만 선택적으로 설정한다. 이 결정은 초기 공유 Bearer 토큰 파일럿 방식을 대체한다.
- 첫 파일럿은 도구 3개를 기본으로 하고, 저작권 조회 수요가 확인되면 4개로 늘린다.
- 일정은 선행 실증 후 정한다. 검증되지 않은 API 제공 범위나 쿼터를 개발 전제로 고정하지 않는다.

## 2. SQLite가 필요한지에 대한 판단

현재 요구에는 SQLite가 꼭 필요한 기능이 없다. 원문 저장과 API 캐싱은 서로 다른 문제이며, 어느 쪽도 지금 관계형 DB를 요구하지 않는다.

| 데이터 | 초기 처리 방식 | 판단 근거 |
| --- | --- | --- |
| 작품·작가·사전 등 공개 API 응답 | 크기가 제한된 프로세스 메모리 TTL 캐시 | 사라져도 API에서 다시 조회할 수 있음 |
| API로 확보 가능한 원문 | 출처·판본을 확인해 가져오고 원문 자체는 변형하지 않음 | 원문 제공 API의 실제 존재와 응답 범위부터 확인해야 함 |
| API에 본문이 없어 별도 확보한 소량의 만료 원문 | 이용 조건을 확인한 UTF-8 텍스트와 JSON 메타데이터 파일 | 작은 읽기 전용 자료 묶음은 SQL 없이 조회 가능 |
| 교사의 본문·초안·검증 결과 | 요청 처리 중에만 사용 | 영구 저장과 공유 캐시가 필요하지 않음 |
| 호출 횟수·오류율 | 내용이 없는 운영 로그와 집계 지표 | 교사 입력을 저장하지 않고 운영 상태를 관측할 수 있음 |

원 설계는 원문을 자체 DB에 미리 적재한다고 가정한다. 따라서 모든 도구가 외부 API만 호출하는 설계는 아니다. 또한 공유마당 API 공식 안내는 메타데이터 조회를 설명하며, 원문 전문 제공 여부는 아직 확인되지 않았다. **API에 작품 정보가 있다는 사실과 원문 전문을 받을 수 있다는 사실을 구분해야 한다.** [공유(만료)저작물 API 안내](https://www.data.go.kr/data/15158766/openapi.do)

본문 API가 확인되면 해당 경로를 사용하고, 없으면 소량의 검수된 파일을 사용하는 방식으로 결정한다. 둘 다 확보되지 않으면 원문 공급 완료로 간주하지 않는다. 교사 제공 텍스트 검증은 독립적으로 개발할 수 있다.

DB 재검토 조건은 사용자별 영구 데이터, 복잡한 검색·갱신, 데이터 간 관계 관리가 실제 요구가 되는 경우다. 여러 인스턴스의 캐시·쿼터 공유가 필요해지면 먼저 공유 캐시의 필요성을 검토한다. 이것이 곧 SQL DB 도입 사유는 아니다.

## 3. 파일럿 범위

| 도구 | 첫 파일럿에서 제공할 범위 | 후속 확장 |
| --- | --- | --- |
| `get_passage` | 확인된 판본의 문단 범위 조회, 출처·권리 근거·해시 반환 | 작품과 판본 확대 |
| `verify_quote` | `quotes[]` 검증, 이어서 지원 형식의 `draft` 검사 | 복잡한 지문·문제 형식 지원 |
| `search_works` | 제목·작가로 작품 탐색, 원문 제공 가능 여부 표시 | 도서관 서지 검색 확대 |
| `check_copyright` | 수요와 데이터가 확인되면 네 번째 도구로 공개 | 근거 소스 확대 |

저작권 도구를 별도로 공개하기 전에도 `get_passage` 내부의 본문 제공 판단은 필수다. 검색 결과의 서지 ID와 원문 판본 ID를 연결하며, 검색 결과가 있다는 이유만으로 원문을 제공하지 않는다.

판본 비교, 작가 소개, 어휘·방언 풀이, 도서 추천, 고전 DB, 형태소 분석은 파일럿 이후로 둔다. 원 설계의 전체 후보는 표 기준 9개이며, 본문의 “8개” 표기는 후속 설계 정리 시 수정한다. 폐기한 `get_public_text` 명칭은 사용하지 않는다.

## 4. 구현 전 실증 — Gate 0

다음 항목은 병렬로 조사하고 결과를 `docs/decisions/`에 짧게 기록한다.

| 확인 항목 | 작업 | 통과 기준 |
| --- | --- | --- |
| 교사의 실제 작업 | 자주 쓰는 작품·판본·문제 유형, 결과물 형식 확인 | 첫 파일럿에서 재현할 작업과 작품 목록 확정 |
| 원문 확보 | 공유마당 API 응답과 원문 다운로드 경로 직접 확인 | 본문 공급 경로 또는 파일 확보 방식, 출처·이용 조건 확인 |
| 작품 검색 | 국립중앙도서관의 샘플 검색, 동명 작품 처리 확인 | 응답 필드와 원문 자료 연결 가능성 기록 |
| 연결 가능성 | 대상 교사 계정과 학교 환경에서 원격 MCP 연결 실증 | 도구 목록 조회와 샘플 호출 성공 |
| 공개 접근 | 로그인 없는 MCP 연결과 공개 운영 한도 확인 | URL만으로 실제 클라이언트 연결·도구 호출 성공 |
| 배포 환경 | 기존 계정, 예산, 콜드스타트 허용 범위 확인 | 컨테이너 플랫폼 한 곳 선택 |

2026-11-01 사용자 결정에 따라 로그인 없는 공개 MCP로 운영한다. 사용자는 URL만 등록하며 OAuth·고정 인증 헤더·URL 토큰을 설정하지 않는다. 외부 기관 API 키는 서버에만 보관한다. 실제 계정의 연결은 별도로 확인한다. [Claude 커스텀 커넥터 안내](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)

키 발급 전에는 합성 fixture로 개발하고, API 제공 범위·쿼터·인증 호환성은 실증 완료로 표시하지 않는다. 핵심 원문 경로가 확보되지 않으면 그 문제를 해결한 뒤 원문 공급 파일럿으로 넘어간다.

실증 작업 목록:

- [ ] 교사에게 자주 쓰는 작품·판본·문제 예시를 받아 첫 시나리오를 정한다. 실제 자료는 동의 없이 저장소에 넣지 않는다.
- [ ] 핵심 API별로 신청 상태, 인증 방식, 검색·상세 응답, 오류 응답, 쿼터와 초기화 기준을 기록한다.
- [x] 공유마당에서 작품 정보와 본문 파일을 각각 어디에서 받는지 확인하고, 원문 하나를 끝까지 확보한다.
- [x] 확보한 판본의 출처·권리 근거·이용 조건과 문단 분리 기준을 기록한다.
- [x] 원문 API 사용 또는 검수 파일 사용 중 첫 구현 경로 하나를 결정한다. 다른 경로를 위한 공통 인터페이스는 미리 만들지 않는다.
- [ ] 도서관 서지 ID와 원문 자료의 식별자가 다를 때 연결할 필드를 확인한다. 제목만 같은 자료는 자동 연결하지 않는다.
- [ ] 교사 계정에서 샘플 서버 연결과 실제 도구 호출을 확인한다.
- [x] 로그인 없는 공개 접근 정책을 결정한다. 사용자별 계정·발급 페이지는 만들지 않는다.
- [x] 첫 배포 플랫폼은 Vercel로 확정했다. 공개 호출량의 운영 측정·파일럿 대상과 성공 기준은 후속 실증으로 남긴다.

교사 인터뷰·키 발급·호스팅 계정처럼 외부 입력이 필요한 항목은 대기 상태와 이유를 적고, PR 00·01 및 `source_text` 기반 검증 개발을 병렬로 진행한다.

## 6. API 캐싱 방법론

캐시는 외부 기관의 공개 데이터 조회 레이어에 둔다. `verify_quote` 전체에 캐시를 걸지 않는다. Vercel은 여러 인스턴스를 만들 수 있으므로 캐시·호출량은 각 프로세스에서만 관리한다. 메모리 캐시가 재시작 시 사라져도 결과의 정확성이 달라지지 않아야 한다.

### 저장 대상과 TTL

아래 값은 원 설계에 기반한 초기안이다. 해당 API를 실제로 도입할 때 이용 조건과 응답 특성을 확인한다. 메모리 캐시의 TTL은 보장 보관 기간이 아니라 재사용 가능한 최대 기간이다.

| 대상 | 초기 TTL | 처리 원칙 |
| --- | --- | --- |
| 서지·작가 정보 | 30일 | 출처와 최초 조회 시각 유지 |
| 사전·방언 정보 | 90일 | API 도입 시 적용 |
| 추천 도서 | 1일 | API 도입 시 적용 |
| 저작권 근거 조회 | 1일을 시작값으로 실증 | 판본에 대응하는 근거가 있어야 본문 제공 가능 |
| 정상 응답의 검색 결과 없음 | 60초 | 반복 호출 감소, 장애와 구분 |
| 인증 실패·쿼터 초과·서버 오류 | 결과 캐싱 제외 | 오류를 빈 검색 결과로 바꾸지 않음 |
| 교사 본문·초안·인용·검증 결과 | 저장 제외 | 캐시 키, 로그, 분석 서비스에도 포함하지 않음 |

### 조회·만료·장애 처리

1. 소스·엔드포인트·실제 검색 조건·응답 형식 버전으로 캐시 키를 만든다. 판본별 결과에는 판본 식별자를 포함하고, 비밀키는 포함하지 않는다.
2. 유효한 캐시가 있으면 반환한다. 없으면 외부 API를 호출하고 응답을 검증한 후 저장한다.
3. 같은 키의 동시 요청은 한 번의 업스트림 호출을 공유한다. 처리 중인 요청 정보는 성공·실패 후 제거한다.
4. 엔트리 수와 전체 바이트 상한을 두고, 넘으면 오래 사용하지 않은 항목부터 퇴출한다. 큰 응답은 캐시에 넣지 않는다.
5. 만료된 결과는 기본적으로 재조회한다. 조회 실패 시 유효한 캐시도 없으면 어느 기관에서 실패했는지 반환한다.
6. 캐시 응답의 `retrieved_at`은 실제 외부 조회 시각으로 유지한다. 캐시 적중 여부와 자료의 시점을 구분해서 표시한다.

오래된 서지 데이터를 장애 시 제공하는 기능은 필요성이 확인되면 허용 기간과 함께 추가한다. 만료된 권리 근거를 장애 우회 수단으로 사용하지 않는다. 캐시 적중률·외부 호출 수·지연·쿼터 오류를 측정해 크기와 TTL을 조정한다.

메모리 캐시는 여러 프로세스나 재시작 사이의 호출량을 공유하지 않는다. 특히 일일 쿼터가 작은 API는 재시작 직후 재호출과 동시 호출량을 실증한다. 캐시만으로 일일 한도를 보장한다고 가정하지 않고, 업스트림 제한 응답과 재시도 대기 시간을 처리한다. 엄격한 통합 사용량 관리가 필요해지면 플랫폼 기능 또는 공유 저장소를 별도 검토한다.

## 7. 원문 정확성과 응답 계약

- 원문 텍스트와 비교용 정규화 텍스트를 분리한다. 비교를 위해 원문을 덮어쓰지 않는다.
- 판본별 문단 번호와 UTF-8 텍스트의 SHA-256 해시 기준을 고정한다. `¶번호`는 원문 문자열에 삽입하지 않고 문단 메타데이터로 반환한다.
- `exact`는 원문과 문자 그대로 일치할 때만 사용한다. NFC·공백·따옴표 등 허용한 정규화 후에만 일치하면 `orthography`로 보고하고 실제 차이를 보여준다. 이는 원 설계의 `exact` 정의에 대한 수정 제안이다.
- 옛 표기를 현대어로 바꾸거나 단어·부정·숫자가 달라진 것을 표기 차이로 통과시키지 않는다.
- 퍼지 비교는 후보 위치를 찾는 데만 사용한다. 짧은 인용·반복 구절·동점 후보는 위치를 확정하지 않고 추가 확인이 필요함을 표시한다.
- 교정본은 제안으로 반환한다. 자동으로 원래 초안을 바꿨다고 간주하지 않고, 교정 결과를 다시 검증한다.
- `quotes`와 `draft`, `work_id`와 `source_text`는 각각 하나만 받도록 입력 계약을 정한다. `work_id`로 조회 결과를 검증할 때는 판본·해시가 같은지 확인한다. 빈 문자열·초과 크기·잘못된 문단 범위를 거부한다.
- `draft`에서 찾은 인용과 검사 범위를 보고한다. 인용을 0개 찾거나 지원하지 않는 표시 형식이면 “검증 완료”로 표시하지 않는다. 빈칸 문제의 검증에는 복원한 인용이 필요하다.
- MCP 서버는 Claude의 최종 답변 전송을 강제할 수 없다. 도구 지시문과 사용 안내에 조회 → 작성 → 검증 → 교정·재검증 절차를 넣고, 검사하지 않은 범위는 미검증임을 표시한다.
- 공통 응답은 `items`, `source`, `copyright`, `retrieved_at`, `note`를 유지한다. 여러 출처·작품을 담는 결과는 항목별 출처·권리 근거도 제공한다.
- 저작권 근거는 작품명이나 작가명만으로 합치지 않고 실제 제공 판본에 연결한다. API에서 찾지 못한 것은 `protected`로 단정하지 않고 `unknown`으로 표시하며, 둘 다 본문 공급은 차단한다.
- 교사 제공 본문은 파일·캐시·로그·오류 추적 서비스에 기록하지 않는다. 이 정책은 우리 서버의 처리 범위에 관한 것이며, Claude의 대화 보관 정책과 구분해 안내한다.

## 8. 검증과 단계별 통과 기준

| 단계 | 검증 내용 | 다음 단계 진입 기준 |
| --- | --- | --- |
| Gate 0: 실증 | 작품·원문 경로·이용 조건·Claude 연결 | 첫 파일럿 작업과 데이터 확보 방식 확정 |
| Gate 1: 로컬 기능 | 원문 무변형, 문단 주소, 검증 엔진, 오류·입력 처리 | 고정한 정답 fixture 통과, 핵심 오인용을 정확 일치로 판정한 사례 0건 |
| Gate 2: 원격 기능 | 실제 Claude 도구 호출, 로그인 없는 공개 연결, 캐시, 장애, 입력 비저장 | 조회 → 초안 작성 → 검증 → 재검증 흐름 재현 |
| Gate 3: 교사 파일럿 | 실제 자료 제작, 다시 사용한 이유, 수정 필요 지점 | 반복 사용과 인용 검증 가치 확인 후 후속 도구 선택 |

정답 fixture는 정확 일치, NFC 차이, 공백·문장부호, 단어 교체, 부정·숫자 변경, 다른 판본, 문단 경계, 반복 구절, 없는 인용을 포함한다. 교사 입력 대신 합성 텍스트나 이용 조건이 확인된 텍스트를 쓴다. “오판정 0건”은 고정한 검증 사례에서의 기준이며 모든 입력에 대한 정확도 보장은 아니다.

CI는 외부 API 키 없이 실행한다. 실제 API 계약 검증은 별도 실행으로 분리하고, 재배포·콜드스타트 후 캐시 소실, 쿼터 초과, 원문 없는 검색 결과도 확인한다. 파일럿의 교사 수와 반복 사용 기준은 Gate 0에서 합의한다.

## 9. 브랜치·배포 연결

- 작업 브랜치 → `develop` PR에서 문서 lint, Python lint·format, 타입 검사, 테스트를 필수 검사로 둔다.
- `develop`은 staging, `main`은 production으로 연결하고 기관 API 키를 환경별로 분리한다.
- Vercel에서는 검증한 소스·잠금 파일·원문 버전을 `main`으로 배포하고 deployment ID·Git SHA를 확인한다. 컨테이너 환경에서는 검증한 이미지 digest로 배포 대상을 고정한다.
- DB가 없으므로 DB 마이그레이션은 없다. 파일형 원문을 사용하는 경우 컨테이너와 함께 버전을 고정해 재배포와 롤백이 가능하게 한다.
- Vercel에서는 원문을 함수 번들에 포함하고 런타임 파일 쓰기·메모리의 영속성을 기대하지 않는다. 루트 `app.py`의 ASGI 앱을 실행한다. [Vercel Python 런타임](https://vercel.com/docs/functions/runtimes/python)
- HTTP 동작·인증·헬스체크는 선택한 FastMCP 버전의 지원 방식으로 연결하고 실제 클라이언트로 검증한다. [FastMCP HTTP 배포](https://gofastmcp.com/deployment/http)
- 초기 단일 인스턴스 중단은 허용 가능한지 파일럿에서 확인한다. 확장은 캐시 중복과 업스트림 쿼터 측정 결과를 기준으로 결정한다.
- 배포 후 도구 목록, 핵심 호출, 오류율을 확인한다. 실패하면 이전 이미지와 자료 버전으로 되돌린다.

## 10. 파일럿 이후 확장 순서

다음 항목은 파일럿의 수요를 확인한 뒤 각각 작은 PR로 진행한다. 전체 후보 도구 9개를 한꺼번에 구현하지 않는다.

| 순서 | 후보 작업 | 시작 조건 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | `check_copyright` 공개 | 교사가 독립적인 권리 확인을 반복 요청하고 근거 데이터가 확보됨 | 만료·보호·불명을 구분하고 판본별 근거와 확인 시각 반환 |
| 2 | `compare_versions` | 실제 수업에 쓰는 비교 대상 판본 2종 이상 확보 | 범위를 맞춘 표기·어휘·문장 차이와 각 출처 반환 |
| 3 | `get_author` | 작가 소개 수요와 번역원 데이터 범위 확인 | 동명이인 구분, 근거 있는 생애·대표작 정보 반환 |
| 4 | `lookup_words` | 교사 자료에서 어휘 풀이가 반복됨 | `words[]`의 뜻풀이·품사·출처 반환, 이후 단락 입력 지원 |
| 5 | `lookup_dialect` | 방언을 포함한 작품에서 실제 요청 발생 | 지역 필터, 대응 표준어와 조사 출처 반환 |
| 6 | `recommend_books` | 독서 지도 수요 확인 | 기간·결과 수를 제한하고 사서 추천 근거와 출처 반환 |

위 순서는 기본안이다. 교사 사용 결과가 다르면 순서를 조정한다. 새로운 API마다 샘플 계약·이용 조건·쿼터를 확인하고 기존 공통 응답·오류·캐시 정책을 재사용한다. 단락 어휘 분석은 `words[]` 조회가 유용한지 확인한 뒤 추가하고, 형태소 분석 라이브러리를 미리 설치하지 않는다.

그다음 단계는 고문헌·고전 원문과 번역이다. 한국고문헌종합목록과 한국고전종합DB의 공식 제공 범위·이용 조건, 이미지와 텍스트 구분, 원문·번역의 권리 근거를 각각 확인한 후 별도 계획으로 나눈다. 번역원 발췌본·해외 서평은 실제 심화 수업 수요가 생겼을 때 검토한다.

도서관 대출·인기 도서는 원 설계대로 정보나루 MCP의 제공 기능을 확인해 함께 연결하는 방식을 검토한다. 이 저장소에서 같은 기능을 중복 구현하지 않는다.

| 관측 결과 | 먼저 할 일 | 재검토할 구조 |
| --- | --- | --- |
| 재시작 후 반복 조회로 쿼터가 자주 소진됨 | 호출량·재시도·TTL·배포 빈도 확인 | 플랫폼 제한 기능 또는 공유 캐시 |
| 동시 사용량이 단일 프로세스 용량을 넘음 | 입력 상한·비용이 큰 비교·지연 측정 | 인스턴스 확대와 공유 캐시·호출량 관리 |
| 사용자별 접근 회수·집계가 필요함 | 인증 요구와 최소 보관 데이터 정의 | OAuth와 사용자 식별 관리 |
| 원문·판본의 검색·갱신이 파일로 관리하기 어려움 | 자료 수와 편집 흐름 측정 | 인덱스 또는 DB의 필요성 |
| 교사가 검증 이력 저장을 요청함 | 필요한 보관 범위·기간과 삭제 요구 확인 | 사용자별 영구 저장소와 별도 보관 정책 |

MVP 로그와 캐시만으로 충분한 동안에는 운영 요소를 늘리지 않는다. 특히 원문 자료가 늘어난다는 이유만으로 관계형 DB를 자동 도입하지 않는다.

남은 외부 실증:

1. 서버 환경에 기관 API 키를 전달받아 인증된 실제 성공 응답과 쿼터를 확인한다.
2. 호스팅 플랫폼·계정·서비스·예산과 운영 비밀값·Host를 확정해 staging에 배포한다.
3. 실제 교사 계정에서 Claude 연결과 조회 → 작성 → 검증 → 재검증을 실증하고, 파일럿 기준을 확정한다.

구현·검증 결과와 스택 PR은 [현재 진행 상태](STATUS.md)에 기록했다. 원격 `develop`을 준비했으며 GitHub 브랜치 보호를 실제 적용했다. 스택 PR은 부모 PR 통합 후 `develop`으로 대상을 바꾸고 최신 `develop`을 작업 브랜치에 정상 병합해 갱신한다. 공유 브랜치를 force-push하지 않는다.

각 작업 종료 시에는 변경 파일, 실행한 검사, 실제 API·클라이언트 검증 여부, 남은 의존성을 기록한다. 모든 필수 PR과 파일럿 검증이 끝난 뒤에만 첫 릴리스 완료로 표시한다.

다운로드 폴더의 기준 설계 문서는 수정하지 않았다. 계획 작성 이후 사용자의 전체 구현 요청에 따라 코드·테스트·문서와 원격 PR 구성을 진행했다. 국립중앙도서관 API 키는 신청 중이며, 한국고전종합DB 접근·이용 조건, 교사 실사용 확인과 후속 production 릴리스는 별도로 기록한다.

## 13. 고전문학·고전시가 지원 계획

사용자가 작품 범위를 소규모로 제한하지 않고 가능한 한 넓히기로 결정했다. 범위 확대는 API에서 실제로 확보 가능한 데이터와 항목별 이용 조건에 따라 진행한다. “고전 작품”의 저작권 만료와 현대 활자화·교감·번역·주석 데이터의 권리는 별개로 확인한다. 원문이 아닌 자료는 권리 근거가 확인될 때만 응답에 포함한다.

PR 12의 요청 입력은 `query`, 제한된 `collection`(`classic`, `anthology`, `corpus`), `limit`으로 최소화한다. API `start` 오프셋을 내부에서만 처리하고 사용자에게 임의 대량 페이지 수집을 허용하지 않는다. 결과에는 원 API의 `자료ID`, 제목·저자·권차·본문 발췌, 원문 상세 링크, 발췌 여부를 제공한다. XML 응답 크기·타임아웃·결과 수를 제한하고 DTD/entity를 거부한다. 정식 API가 검색만 제공하므로 이를 `get_passage` 전문 조회 성공으로 표시하지 않는다.

한국고전종합DB API는 신청 키 없이 사용 가능하므로 PR 12에서 실제 검색 호출을 먼저 구현한다. 국립중앙도서관 키 발급은 별도 필요조건으로 유지한다. 전체 목록 자동 수집이나 무제한 동기화는 API 허용량·권리를 확인하기 전 구현하지 않는다.

### 문법·고전 문법 도구 후보

기존 후속 후보에는 `lookup_words`와 형태소 분석 검토가 있었지만, 별도 문법·고전 문법 도구는 정의되지 않았다. 문법 개념·출처·고전어 형태·원문 용례를 제공하는 `lookup_grammar` 후보 하나로 좁힌다. 상세 입력·응답은 ITKC 검색 연동 기록에 둔다. 근거 자료가 확보되면 PR 16에서 확정한다.

### 공통 완료 기준

- API 검색 결과, 원문 전문, 디지털 이미지, 현대 전사·교감문, 번역·주석을 서로 다른 제공물로 표시한다.
- 자료마다 이용 조건, 출처표시, 상업 이용·변경·재배포 허용 여부를 기록한다. 기관의 공공누리 표기가 타 권리자의 요소까지 허용한다고 간주하지 않는다.
- 키와 교사 입력은 저장소·fixture·로그에 남기지 않는다. API 장애와 미허용·불명 자료를 빈 성공으로 숨기지 않는다.
- 제목만으로 목록 레코드와 텍스트 판본을 연결하지 않는다. 고유 ID 또는 검토한 명시적 매핑을 사용한다.
- 작품 수 자체가 아니라 개별 제공 텍스트의 권리·무결성·주소 정확성을 모두 충족해야 제공한다.
